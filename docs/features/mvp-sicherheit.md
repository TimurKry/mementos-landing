# Feature: Sicherheit im MVP (`mvp/`) — Rechtemodell, Sitzungen, Kopfzeilen

Итерация по безопасности динамического MVP (`mvp/` — отдельное Next-приложение
с БД и auth, **не** GitHub Pages). Закрыты две критические дыры эскалации
привилегий в модели доступа (`0004_hardening.sql`) и один open redirect,
найденный независимым ревью уже после первого прохода (`src/lib/safe-next.ts`).

Читать перед любой правкой SQL-функций, middleware или потока приглашений.
Немецкая копия и идентификаторы приведены как в коде.

> Ни одно утверждение ниже не является обещанием соответствия чему-либо.
> Юрлицо, AVV, договор хостинга, сроки хранения — открыты (см. последний раздел).

---

## Что защищаем и от кого

Домен: один Fall (Vorgang) ведёт Bestatter, остальные участники (Familie,
Krematorium, Transport, Friedhof …) входят **без аккаунта по ссылке** и должны
видеть только поля своей роли. Отсюда модель угроз:

| Актор | Что имеет | Чего не должен получить |
|---|---|---|
| Аноним (PostgREST, `anon`-ключ публичен по определению) | URL проекта + `anon`-ключ | ничего о делах |
| Держатель законной ссылки (Familie) | валидный токен своей роли | поля других tier'ов, `case_id`, внутренние названия фирм-партнёров |
| Второй аутентифицированный Bestatter | свой аккаунт | чужие Fälle (IDOR) |
| Тот, кто получил ссылку из пересланного письма/скриншота | токен из адресной строки | долгоживущий доступ |

Ключевые данные, из-за которых цена ошибки высока: `sens`-tier
(`herzschrittmacher`, `infektionshinweis`, `freigabe_einaescherung`) и
внутренние названия фирм-партнёров.

## Дыра #1 — эскалация через дефолтный `GRANT PUBLIC`

В PostgreSQL `CREATE FUNCTION` по умолчанию выдаёт `EXECUTE` роли `PUBLIC`.
В `0003_access.sql` функции `get_case_for_role(uuid, role)` и
`deceased_for_role(uuid, role)` были `SECURITY DEFINER` (то есть **обходили
RLS**), а права никто не отзывал. Аноним через PostgREST мог вызвать

```
get_case_for_role('<case-uuid>', 'bestatter')
```

и получить все поля дела, включая медицинские.

## Дыра #2 — эскалация из легитимной ссылки

`resolve_invite(token)` был выдан `anon` и возвращал `case_id`. Цепочка без
всякого подбора:

1. держатель законной семейной ссылки вызывает `resolve_invite(<свой токен>)`
   → получает `case_id`;
2. вызывает `get_case_for_role(case_id, 'bestatter')`
   → получает медицину и внутренние названия фирм-партнёров.

## Корень обеих дыр

**Роль передавалась аргументом, а не читалась из строки приглашения.** Всё
остальное — следствие: раз роль подставляет вызывающий, любая доступная ему
функция фильтрации становится функцией повышения прав.

## Как закрыто: `mvp/supabase/migrations/0004_hardening.sql`

Инвариант после миграции: роль читается сервером из `public.invites`,
`case_id` наружу не отдаётся никогда, публичный контракт — ровно три функции.

### Порядок в файле — часть защиты

- **`alter default privileges … revoke execute on functions from public, anon`
  стоит в самом верху, до первого `create function`.** Эта команда **не
  действует ретроактивно**: если поставить её ниже, все созданные выше функции
  снова унаследуют `PUBLIC EXECUTE`, а миграция при этом пройдёт «зелёной».
  Выполняется для схем `public` и `app`.
- **Старые функции `DROP`, а не `CREATE OR REPLACE`.** `CREATE OR REPLACE` с
  новой сигнатурой создал бы **перегрузку**: старая дырявая версия осталась бы
  жить со своим `PUBLIC EXECUTE`, а внешне миграция выглядела бы успешной.
  ACL исчезает вместе с функцией — это и есть основной механизм закрытия #1 и
  #2. Удалены: `get_case_by_invite`, `resolve_invite`, `get_case_for_role`,
  `deceased_for_role`, `allowed_tiers` (в `public`).
- **`is_case_owner(uuid)` не дропается** — на ней висят RLS-политики из
  `0002_rls.sql`; она только переопределяется с `set search_path = ''`.

### Что где лежит

- Внутренние функции переехали в схему `app`: `allowed_tiers`,
  `deceased_for_role`, `case_for_role`, `log`, `hash_token`, `new_token`,
  `set_case_ref`, `handle_new_user`, `audit_log_append_only`. У `anon` и
  `authenticated` **нет `USAGE`** на `app`; PostgREST экспонирует только
  `public` — значит по HTTP они недостижимы. Внутри `SECURITY DEFINER` права
  проверяются против владельца, поэтому `public.get_case_by_session` →
  `app.case_for_role` работает.
- У анонима ровно пять функций: `redeem_invite(text)`,
  `get_case_by_session(uuid)`, `end_session(uuid)`, с `0011` —
  `termin_bestaetigen(uuid, uuid, timestamptz, timestamptz, text)`, с `0012` —
  `angaben_ergaenzen(uuid, jsonb)`. Две последние — единственные пути записи
  из-за периметра; см. раздел «Приглашённый, который пишет».
- **`is_case_owner` нельзя отзывать полностью.** Выражения RLS-политик
  исполняются от **вызывающей** роли, поэтому ей выдан `EXECUTE` для
  `authenticated`. Симптом, если это забыть: `permission denied for function
  is_case_owner` и полный отказ RLS. Комментарий об этом стоит прямо в файле.
- `grant usage on schema public to anon` остаётся — без него не работает
  PostgREST.

### Приглашённый, который пишет (`0011_termine.sql`)

До `0011` внешний периметр был **только для чтения**: аноним обменивал токен
на сессию, читал свой срез и закрывал сессию. Термины это изменили — водитель
подтверждает время забора, крематорий время кремации. Это первый и пока
единственный путь записи из-за периметра, поэтому он разобран отдельно.

**Две матрицы, а не одна.** Видеть и менять — разные права, и они намеренно
расходятся:

| роль | видит типы событий | имеет право подтверждать |
|---|---|---|
| `transport` | `abholung`, `ueberfuehrung` | `abholung`, `ueberfuehrung` |
| `krematorium` | `ueberfuehrung`, `einaescherung` | только `einaescherung` |
| `friedhof` | `beisetzung` | `beisetzung` |
| `familie` | `abholung`, `abschiednahme`, `trauerfeier`, `beisetzung` | — |
| `floristik` / `redner` / `steinmetz` | церемонии своей роли | — |
| `standesamt` / `verbund` | ничего | — |

Флористика, оратор и каменотёс по матрице полей (`app.allowed_tiers`, `0004`)
не видят об умершем **ничего** — ни имени, ни даты. Это осталось как было.
Время и место церемонии они получают через событие, и ни одного поля о
человеке при этом не открывается.

**Что проверяет `public.termin_bestaetigen`** — по порядку, до любой записи:

1. сессия жива, приглашение не отозвано и не истекло;
2. событие принадлежит **тому же делу**, что и сессия. Без этой проверки
   действительная сессия позволила бы менять событие чужого дела — id события
   приходит из формы;
3. `app.darf_bestaetigen(роль, тип)` разрешает именно этот тип.

Ни `case_id`, ни роль в функцию не передаются: и то и другое берётся из
приглашения по сессии. Сессия лежит в `httpOnly`-cookie, не в форме.

**В журнал идёт только `{art, role}`.** Адрес и примечание — свободный текст;
там может оказаться что угодно, и в аудит это не попадает.

Возврат — `boolean`, а не исключение: «не положено» и «сломалось» должны
различаться в интерфейсе, иначе человек десять раз повторит то, на что у него
просто нет права.

### Четвёртая матрица: кто вправе МЕНЯТЬ поля (`0012_angaben_der_familie.sql`)

Матриц теперь четыре, и они намеренно не совпадают:

| матрица | вопрос | где |
|---|---|---|
| `app.allowed_tiers` | какие группы полей роль **видит** | `0004` |
| `app.termine_fuer_rolle` | какие типы событий видит | `0011` |
| `app.darf_bestaetigen` | какие события вправе подтверждать | `0011` |
| `app.felder_schreibbar` | какие поля вправе **менять** | `0012` |

Семья **видит** группы `kern`, `org` и `op` — а менять вправе только пять
полей: `vorname`, `nachname`, `geburtsdatum`, `konfession`, `anschrift`.
Sargmaß и вес измеряет бюро, а не дочь покойной.

`sterbedatum` в списке нет намеренно: оно стоит в свидетельстве о смерти. Что
пришло из документа, не переписывается по памяти.

**Клиника сознательно НЕ получила права писать в группу `sens`**
(кардиостимулятор, инфекционная опасность, разрешение на кремацию). По сути
это было бы правильно — клиника знает лучше всех. Но это самая чувствительная
группа, и открывать её на запись по ссылке без аккаунта — отдельное решение,
которому не место в миграции, делающей попутно другое. До тех пор `sens`
остаётся только у бюро.

**Что проверяет `public.angaben_ergaenzen`** — по порядку, до любой записи:

1. `p_felder` вообще объект JSON;
2. сессия жива, приглашение не отозвано и не истекло;
3. у роли есть хоть какое-то право записи, иначе `false`;
4. для каждого разрешённого поля, которое пришло: тип — строка или `null`
   (объект или число отвергаются целиком), нет управляющих символов, длина в
   пределах `app.feld_grenze`, дата не только по маске, но и существующая
   (`2026-02-31` отвергается);
5. поле, которое роли не положено, **не отвергается, а пропускается** — иначе
   по сообщению об ошибке можно было бы прощупать, какие поля вообще есть.

Любая неудачная проверка на шаге 4 отменяет **весь** вызов: половина данных
не должна доезжать. Пропущенный ключ остаётся нетронутым, явный `null` —
стирает значение.

**В журнал идут ИМЕНА полей, никогда содержимое:**
`{"role":"familie","felder":["geburtsdatum","konfession","anschrift"]}`.

Проверено на живом PostgreSQL 16 по всей цепочке `0001`–`0012`: 15 сценариев,
включая попытку транспорта писать имя, запись в `sargmass` под видом
разрешённого вызова, невозможную дату, 201 символ в адресе, управляющий
символ, отозванный доступ и прямой `update` от роли `anon`.

### Почему все публичные функции `VOLATILE`, а не `STABLE`

Они пишут аудит, поэтому `VOLATILE` формально корректно. Полезный побочный
эффект: PostgREST разрешает `GET` только для `stable`/`immutable`, значит эти
три достижимы **только через POST** — токен и идентификатор сессии не попадают
в query string и access-логи.

### Гигиена `search_path`

Все функции — с `set search_path = ''`, все объекты полностью
квалифицированы, включая литералы enum (`'familie'::public.role`). Так ничего
неквалифицированного не разрешается и атаки через `pg_temp` уходят в пустоту;
`pg_catalog` остаётся доступным неявно.

### Токены

- В БД только `sha256` — `invites.token_hash` (`app.hash_token`), колонка с
  открытым текстом **удалена**. Открытый текст возвращается из `create_invite`
  ровно один раз и после этого не восстановим.
- Токен — 64 hex-символа: две склеенные `gen_random_uuid()` (256 бит из
  `pg_strong_random`).
- `pgcrypto` сознательно **не** используется: в Supabase он в схеме
  `extensions` и при `search_path=''` потребовал бы квалификации
  `extensions.digest`. Встроенная `sha256()` из `pg_catalog` этого не требует.
- Существующие токены при миграции переносятся **в виде хеша, но сразу
  помечаются `revoked = true`**: они лежали в базе открытым текстом, значит
  считаются скомпрометированными. Хеш нужен только чтобы сработали
  `NOT NULL` и `UNIQUE`; новые ссылки Bestatter выдаёт через `create_invite`.
  При новой установке таблица пуста, и блок не делает ничего.
- `CHECK invites_role_not_bestatter` — ссылку с ролью `bestatter` выдать
  нельзя. Иначе одна опечатка в UI дала бы вход **без аккаунта с полным
  доступом**. Ограничение добавляется `not valid`, затем `validate` — на
  существующих данных с такой строкой миграция намеренно упадёт.

### Сессии вместо долгоживущего токена в URL

`public.invite_sessions` (12 часов, `ended_at`, `last_seen_at`) даёт немедленный
отзыв, короткое время жизни, стабильный идентификатор для журнала и
возможность убрать токен из адресной строки. RLS: видит и обновляет только
владелец дела; `INSERT`/`DELETE` отозваны у всех — строки создаёт только
`public.redeem_invite`.

`revoke_invite` закрывает и все живые сессии этого приглашения — **отзыв
действует немедленно**, а не по истечении срока.

### Функции владельца проверяют владение сами

`create_invite`, `list_invites`, `revoke_invite`, `revoke_session` вызывают
`is_case_owner` **внутри себя**, потому что `SECURITY DEFINER` обходит RLS и
полагаться на политику здесь нельзя. Отказ — `Kein Zugriff …`, errcode `42501`.

### Журнал `audit_log` — только append

- Append-only обеспечивает триггер **уровня оператора** (`for each statement`)
  с `before update or delete or truncate`. `TRUNCATE` включён сознательно:
  построчный триггер его не поймал бы, и журнал стёрся бы одной командой.
  Триггер срабатывает и для владельца таблицы — обычные `GRANT`/`REVOKE` этого
  не дают.
- Пишет только `app.log()` (`SECURITY DEFINER`); `INSERT/UPDATE/DELETE` на
  таблице отозваны у `public`, `anon`, `authenticated`.
- Действия: `invite.redeem`, `invite.redeem.failed`, `invite.create`,
  `invite.revoke`, `session.end`, `session.revoke`, `case.view`.
- `case.view` дросселируется — не чаще одного раза в 5 минут на сессию, иначе
  журнал распухает от каждого ре-рендера интерфейса.
- **IP и User-Agent не пишутся** — минимизация данных (открытый вопрос, см.
  ниже). `case_id` у `audit_log` стал nullable: неудачная попытка обмена не
  относится ни к какому делу.

### Два побочных исправления в схеме

- `cases.ref` теперь генерирует триггер `app.set_case_ref()`
  (`M-YYYY-XXXXXX`) вместо `floor(random()*9999)`: некриптостойкий `random()`
  на 4 цифры при `UNIQUE NOT NULL` по парадоксу дней рождения давал коллизии
  примерно со 118 записей — то есть отказы вставки. Триггер `SECURITY DEFINER`,
  потому что проверка коллизии должна видеть все дела, а под RLS видела бы
  только свои.
- Триггер `app.handle_new_user()` на `auth.users` создаёт `public.profiles`
  при регистрации: без него новый Bestatter не смог бы создать ни одного Fall
  (нарушение внешнего ключа `cases.owner`).

## Приложение (Next 15, `mvp/src/`)

### Токен ушёл из адресной строки

`/einladung/<токен>` — **Route Handler**
(`src/app/(extern)/einladung/[token]/route.ts`), а не страница: проверяет форму
токена (`/^[0-9a-f]{64}$/`), обменивает его через `redeem_invite`, ставит
cookie `mos_zugang` и отдаёт `303` на `/zugang`.

Почему именно Route Handler: `cookies().set()` из Server Component в Next 15
бросает исключение — cookie можно ставить только в Route Handler или Server
Action.

Cookie (`src/lib/zugang.ts`): `httpOnly`, `sameSite=lax`, `path=/`, 12 часов,
`secure` только когда соединение по HTTPS (Next учитывает
`X-Forwarded-Proto`; на `http://localhost` флаг тихо убил бы демо). Подпись не
нужна — значение случайное и проверяется на сервере при каждом обращении
(`get_case_by_session`).

### Три исхода обмена — разделены сознательно

| Исход | Куда |
|---|---|
| токен неизвестен / отозван / истёк / не той формы | `/einladung/ungueltig?grund=ungueltig` |
| сбой сети или БД | `/einladung/ungueltig?grund=technik` |
| пользователь сам нажал «Zugang beenden» | `/einladung/ungueltig?grund=beendet` |

«Ihr Link ist abgelaufen» и «bitte in einigen Minuten erneut» — для семьи две
совершенно разные вести. Именно поэтому `redeem_invite` при неудаче возвращает
`NULL`, а **не** бросает исключение: исключение означает только техническую
неисправность, и слой данных (`src/lib/data.ts`) отличает одно от другого.

`zugangBeendenAction` закрывает сессию на сервере (`end_session`) **и** удаляет
cookie — одного из двух недостаточно.

### Два разделённых периметра

Route groups:

- `(intern)` — дашборд, `/fall/**`, навигация, `Abmelden`;
- `(extern)` — `/login`, `/einladung/**`, `/zugang`, без единой ссылки в
  рабочий контур.

Раньше общий layout показывал приглашённой семье навигацию внутреннего
контура.

### Вход

Только magic-link, паролей нет (`src/app/(extern)/login/LoginForm.tsx`):

- `shouldCreateUser: false` — иначе любой человек с почтой заводит себе
  аккаунт в рабочем контуре;
- ответ формы всегда одинаковый, существует адрес или нет (защита от
  перечисления пользователей — иначе через форму можно было бы выяснять, какие
  дома здесь работают);
- `/auth/abmelden` — **только POST**: GET-выход срабатывал бы с чужой страницы
  одним `<img src>`.

### Middleware (`src/middleware.ts`)

Порядок: **конфигурация → заголовки → периметры**.

1. `assertRuntimeConfig()` первым: полуконфигурация — самое опасное состояние,
   поэтому здесь она обрывается ответом `500` с текстом
   «MementoOS: Die Anwendung ist nicht vollständig konfiguriert.»
2. Заголовки безопасности на **каждый** ответ, включая аварийный.
3. `/zugang` — только с cookie правильной формы (`isSessionId`); валидность
   проверяет сама страница через `get_case_by_session`, обращения к БД в
   middleware нет.
4. Рабочий контур (`/` и `/fall/**`) в live-режиме требует
   аутентификации. **Fail-closed:** сбой `getUser()` тоже ведёт на `/login`.

Matcher покрывает всё, кроме `_next/`, `favicon.ico`, `robots.txt`.

### Fail-loud вместо тихого mock (`src/lib/env.ts`)

- задан только URL или только ключ → бросает **всегда**;
- ничего не задано и `NODE_ENV=production` → старт прерывается, если не задан
  явный `MEMENTO_ALLOW_MOCK=1`;
- сборка исключена (`NEXT_PHASE=phase-production-build`), иначе `pnpm build`
  в mock-режиме перестал бы быть зелёным. Проверка срабатывает в рантайме —
  её проходит каждый вызов слоя данных.

### Заголовки (`src/lib/security-headers.ts`)

- CSP с nonce: `script-src 'self' 'nonce-…' 'strict-dynamic'` — в продакшене
  **без единой `unsafe`-директивы**; `'unsafe-eval'` добавляется только в dev.
  `style-src 'unsafe-inline'` в App Router неизбежен и не ослабляет контроль
  над скриптами. Плюс `object-src 'none'`, `base-uri 'none'`,
  `frame-ancestors 'none'`, `frame-src 'none'`, `form-action 'self'`;
  `connect-src` включает URL проекта только в live-режиме.
- nonce — 16 байт из `crypto.getRandomValues`, свежий на каждый запрос;
  прокидывается в `x-nonce`, чтобы Next подписал свои script-теги.
- `Referrer-Policy: no-referrer` — **сайт-wide**, не только на `/einladung`:
  частичное правило теряется при следующем рефакторинге.
- `X-Content-Type-Options`, `X-Frame-Options: DENY`,
  `Cross-Origin-Opener-Policy`, `Permissions-Policy`, `X-Robots-Tag`,
  `Strict-Transport-Security` (**без `preload`** — домен не решён, а preload
  практически необратим).
- `Cache-Control: no-store` на страницах с данными дела и на путях
  авторизации.
- `next.config.ts` повторяет статические строки как вторая линия (если
  middleware однажды не сработает); CSP остаётся за middleware — ей нужен
  свежий nonce на запрос. `poweredByHeader: false`.

### service_role

Читается только в `src/lib/env.ts` за `import "server-only"`. Точек вызова у
`supabaseService()` **пока нет вовсе**; в клиентский бандл ключ не попадает.
Публичные значения живут отдельно в `src/lib/public-env.ts`, чтобы
браузерный клиент не импортировал серверный модуль.

## Уязвимость, найденная независимым ревью после первого прохода

### Open redirect через управляющие символы в `?next=`

Проверка сравнивала префиксы строки: `/` — да, `//` и `/\` — нет. Но **парсер
URL удаляет ASCII-таб (0x09), LF (0x0A) и CR (0x0D) до разбора**. Значение вида
«слэш + таб + слэш + домен» не равно `//` и не равно `/\`, проходит все три
префиксных проверки, а затем разбирается как `//домен` — то есть чужой origin.
В процентной кодировке значение проходило и через строку запроса, потому что
`searchParams.get()` декодирует **раньше** проверки.

Сценарий: ссылка `?code=<валидный>&next=%2F%09%2Ffremde.example` — после
успешного входа человек оказывается на чужой странице, **уже будучи
аутентифицированным**. Готовая основа для поддельной формы входа.

Исправление — `src/lib/safe-next.ts`, один хелпер на проект:

1. отклонить управляющие символы (всё до 0x20 включительно и 0x7f);
2. **разрешить URL относительно базы и сравнить origin**, вместо угадывания
   префиксов;
3. вернуть `pathname + search` (фрагмент серверу не нужен), иначе `/`.

Используется и в `/auth/callback`, и в middleware (`?next=` при редиректе на
`/login`). Без `server-only`: тот же файл исполняется в Edge-middleware.

**Урок:** любое «is this URL local?» решается разрешением и сравнением origin.
Сравнение префиксов строки не работает никогда.

### Заодно: `toggleTask`

`src/lib/data.ts` — `toggleTask` теперь привязан к паре (`case_id`, `task_id`).
Раньше `caseId` принимался, но в запросе не использовался: одной задачи хватило
бы, чтобы попасть в чужую, если правило RLS `tasks_owner` ослабят или потеряют.

## Чем проверено (честно — что вживую, что чтением)

- Миграции `0001`→`0007` применены на **боевом проекте Supabase**
  (PostgreSQL 17, регион `eu-west-3`) и проверены там же: цепочка эскалации
  падает на каждом шаге, роль `familie` не получает медицинских полей, роль
  `krematorium` не получает конфессию и адрес, названия фирм скрыты, отзыв
  ссылки немедленно закрывает живую сессию, журнал неизменяем даже для
  владельца БД, дело удаляется полностью и журнал при этом уцелевает.
  Линтер безопасности Supabase не нашёл ничего сверх наших восьми
  намеренных функций публичного контракта.
- Миграции `0001`→`0004` прогнаны на **живом PostgreSQL 16**, трижды подряд —
  идемпотентно.
- Цепочка эскалации проверена **от роли `anon`**: `resolve_invite` и
  `get_case_for_role` не существуют; `app.case_for_role` →
  `permission denied for schema app`; прямое чтение `deceased`, `invites`,
  `cases`, `audit_log` → `permission denied` на всех четырёх.
- Фильтрация проверена **по байтам ответа**, а не по внешнему виду:
  - `familie` → `kern+org+op`, без `herzschrittmacher`, `infektionshinweis`,
    `freigabe_einaescherung`;
  - `krematorium` → `kern+op+sens`, без `konfession`, `anschrift`,
    `geburtsdatum`;
  - `floristik` → пустой объект;
  - внутренние названия фирм скрыты у всех, кроме владельца.
- IDOR: второй аутентифицированный пользователь получает `Kein Zugriff` от всех
  четырёх функций владельца.
- Обходы middleware путями: `//fall/x`, `/./fall/x`, `/foo/../fall/x`,
  `/fall%2Fx`, `/FALL/x` — все упираются в защиту. Next 15.5.21, поэтому
  CVE-2025-29927 (обход через `x-middleware-subrequest`) не применима.
- Матрица прав сверена между TS-зеркалом `src/lib/access.ts` и SQL
  `app.allowed_tiers` — совпадает по всем восьми ролям с непустым набором
  tier'ов.
- Open redirect: tab, LF, CR, `//`, `/\` и абсолютные URL после исправления
  разрешаются на свой origin; легитимные пути сохраняются.
- `pnpm build` в `mvp` зелёный **без единой переменной окружения**; лендинг
  по-прежнему зелёный (17 маршрутов).

## Чеклист перед провижном Supabase

Выполнять по порядку; реальные данные заводить **только после** последнего
пункта.

1. Создать проект в регионе **ЕС**. Действующий проект развёрнут в
   `eu-west-3` (Париж); подойдёт и `eu-central-1` (Франкфурт) — важно, что
   данные остаются в ЕС.
2. Прогнать миграции строго по порядку: `0001_init.sql` → `0002_rls.sql` →
   `0003_access.sql` → `0004_hardening.sql` → `0005_grants_final_sweep.sql`
   → `0006_fall_loeschbar_machen.sql` → `0007_audit_ohne_fremdschluessel.sql`.
   `0004` не опциональна: без неё
   функции фильтрации из `0003` вызываются анонимно и роль остаётся аргументом.
3. Выполнить диагностические запросы из блока `Verifikation` в конце
   `0004_hardening.sql` (по одному, они закомментированы). Ожидаемые
   результаты:
   - **ни одной нашей функции с `proacl is null`** (запрос 1) — `null` означает
     `PUBLIC EXECUTE`;
   - у `anon` **ровно пять** `EXECUTE`: `redeem_invite`,
     `get_case_by_session`, `end_session`, `termin_bestaetigen`,
     `angaben_ergaenzen` (запрос 2; до `0011` их три, до `0012` — четыре);
   - все четыре `to_regprocedure(...) is null` → `true`: старых сигнатур нет
     (запрос 3);
   - `has_schema_privilege('anon','app','usage')` = **false** (запрос 4);
   - **колонки `invites.token` не существует** — 0 строк (запрос 5);
   - `invites_role_not_bestatter` есть и `convalidated = true` (запрос 6);
   - `update`/`delete` по `audit_log` падают с «audit_log ist ausschliesslich
     anfügbar» (запрос 7);
   - табличных прав у `anon` в `public` нет — 0 строк (запрос 8).
4. **Никогда не запускайте `0001`–`0003` повторно на уже развёрнутой базе.**
   Они не идемпотентны и упадут — но `0003` успевает выполнить
   `create or replace` для `allowed_tiers`, `deceased_for_role` и
   `get_case_for_role` **до** падения. То есть повторный прогон воссоздаёт
   ровно те уязвимые функции, которые убирает `0004`, и оставляет их с
   дефолтным `PUBLIC EXECUTE`. Если это всё же произошло — немедленно
   прогоните `0004`→`0008` следом и убедитесь запросом 3, что старых
   сигнатур снова нет.

5. Если запрос 1 нашёл **чужие** функции (расширения, объекты самой Supabase) —
   **не трогать их**: ни `revoke`, ни `drop`. Выписать списком и решить
   отдельно. Правило записано и в шапке миграции.
6. Проверить, что `SUPABASE_SERVICE_ROLE_KEY` **не** попал ни в одну переменную
   с префиксом `NEXT_PUBLIC_` (`.env.local`, настройки хостинга, CI). Он
   обходит RLS.
7. Только теперь заводить реальные данные.

Заголовки после деплоя проверяются curl'ом (см. `mvp/README.md`, раздел
*Build & Verifikation*).

## Что осознанно осталось открытым

- **Live-режим проверен только чтением кода.** Проекта Supabase не существует,
  поэтому `getUser()` и обмен кода на сессию вживую не прогонялись.
  Исправление open redirect подтверждено юнит-тестом хелпера, а не живым
  запросом: в mock-режиме `/auth/callback` всегда уходит на `/login`.
- **Storage не покрыт.** Бакета для документов ещё нет. Когда появится, он
  обязан быть приватным (`public = false`) и получить свои правила доступа.
  Функция `document_path_for_session` и прокси-роут для скачивания отложены
  вместе с ним. Интерфейс пока показывает только названия и статус документов.
- **Сроки хранения данных не определены** — требуется юридическая проверка до
  того, как в базу попадут реальные данные.
- **Юрлицо, AVV, договор хостинга** — открыты.
- **Писать ли IP в журнал доступа** — открытый вопрос: минимизация данных
  против прослеживаемости инцидентов (сейчас не пишется даже при неудачных
  попытках обмена, значит систематический перебор в журнале не различим).
- **`HSTS preload` не включён сознательно**, пока не определён домен: запись в
  браузерный список практически необратима.
- `/_not-found` пререндерится при сборке и потому не получает nonce (данных
  дела не содержит).
- `favicon.ico` отсутствует — один 404 в консоли при первой загрузке.
- **Троттлинг попыток разгадать токен не делается сознательно:** 122 бита
  энтропии у uuid v4 и поиск по `sha256` делают онлайн-перебор непрактичным.
  Покрытие обеспечивают аудит неудачных попыток (`invite.redeem.failed`), TTL
  и мгновенный отзыв.
