# MementoOS — где мы сейчас

Карта проекта на 27 июля 2026. Схемы отдельно по темам, чтобы не читать одну простыню.

## 1. Что вообще есть в репозитории

Два самостоятельных приложения в одном репозитории. Они не связаны кодом и деплоятся по-разному.

```mermaid
flowchart TB
    subgraph repo["Репозиторий TimurKry/mementos-landing"]
        direction TB
        subgraph land["Лендинг — корень репозитория"]
            L1["Статический экспорт<br/>17 страниц"]
            L2["Три дизайн-системы:<br/>Monad · Steep · Default"]
        end
        subgraph mvp["MVP — папка mvp/"]
            M1["Динамический Next<br/>серверный рендеринг"]

        end
    end

    land -->|"push в main"| GH["GitHub Pages<br/>публичный сайт"]
    mvp -->|"нужен Node-рантайм"| NODE["ещё не задеплоен"]

    style GH fill:#2b59d1,color:#fff
```

**Важно:** лендинг живой и опубликован. MVP работает локально, база подключена, но само приложение никуда не выложено — для него нужен сервер, GitHub Pages не подойдёт.

## 2. Модель данных

Один `Fall` (дело) — центр всего. Поля умершего разбиты на четыре группы, и именно группы решают, кто что видит.

```mermaid
erDiagram
    profiles ||--o{ cases : "владеет"
    cases ||--|| deceased : "1:1"
    cases ||--o{ participants : "участники"
    cases ||--o{ tasks : "задачи"
    cases ||--o{ documents : "документы"
    cases ||--o{ invites : "выданные ссылки"
    invites ||--o{ invite_sessions : "открытые сессии"
    cases ..o{ audit_log : "журнал, без внешнего ключа"

    profiles {
        uuid id PK "= auth.users"
        text org_name
    }
    cases {
        uuid id PK
        text ref "M-2026-431849"
        uuid owner FK
        enum phase "neu…abschluss"
    }
    deceased {
        text vorname "kern"
        text nachname "kern"
        date geburtsdatum "org"
        text konfession "org"
        text anschrift "org"
        int groesse_cm "op"
        int gewicht_kg "op"
        bool herzschrittmacher "sens"
        text infektionshinweis "sens"
        bool freigabe_einaescherung "sens"
    }
    invites {
        uuid id PK
        bytea token_hash "sha256, НЕ текст"
        enum role "никогда не bestatter"
        bool revoked
    }
    invite_sessions {
        uuid id PK "живёт в cookie"
        timestamptz expires_at "12 часов"
    }
    audit_log {
        text action
        jsonb detail "роль + группы полей"
    }
```

Обрати внимание на пунктир: `audit_log` **намеренно** без внешнего ключа на `cases`. Почему — в разделе 6.

## 3. Кто какие поля видит

Это ядро продукта. Одно дело хранится один раз, но каждая роль получает свой срез.

```mermaid
flowchart LR
    subgraph tiers["Группы полей"]
        K["kern<br/>имя, фамилия"]
        O["org<br/>даты, конфессия, адрес"]
        P["op<br/>рост, вес, размер гроба"]
        S["sens<br/>кардиостимулятор,<br/>инфекция, разрешение"]
    end

    B["Bestatter<br/>ведёт дело"] --> K & O & P & S
    F["Familie"] --> K & O & P
    KR["Krematorium"] --> K & P & S
    T["Transport"] --> K & P
    FR["Friedhof / Standesamt"] --> K & O
    KL["Klinik"] --> K & P & S
    V["Verbund"] --> K
    FL["Floristik / Redner<br/>Steinmetz"] -.->|"ничего"| X["—"]

    style S fill:#c0392b,color:#fff
    style B fill:#f2f2f2,color:#000
    style X fill:#333,color:#888
```

Два примера, проверенные на боевой базе:

| Роль | Получает | Не получает |
|---|---|---|
| **Familie** | имя, даты, конфессия, адрес, рост, вес, размер гроба | **ничего медицинского**, названия фирм-партнёров |
| **Krematorium** | имя, рост, вес, размер гроба, **кардиостимулятор, разрешение** | конфессия, адрес, дата рождения |

Ключевое: непозволенное поле **не приходит вообще**. Оно не скрыто в браузере — его нет в ответе сервера.

## 4. Как участник попадает в дело

Вход по ссылке, без аккаунта. Токен при этом не остаётся в адресной строке.

```mermaid
sequenceDiagram
    autonumber
    participant B as Bestatter
    participant A as Приложение
    participant DB as Supabase
    participant F as Семья

    B->>A: «выдать ссылку роли familie»
    A->>DB: create_invite(дело, роль)
    DB->>DB: токен 64 hex → хранит только sha256
    DB-->>A: токен (единственный раз)
    A-->>B: показывает ссылку один раз
    Note over B: копирует и отправляет семье

    F->>A: GET /einladung/‹токен›
    A->>DB: redeem_invite(токен)
    DB->>DB: хеш → ищет приглашение<br/>не отозвано? не истекло?
    DB-->>A: id сессии (НЕ id дела)
    A-->>F: 303 → /zugang<br/>Set-Cookie: сессия, HttpOnly
    Note over F: в адресной строке /zugang,<br/>токена больше нет нигде

    F->>A: GET /zugang (с cookie)
    A->>DB: get_case_by_session(сессия)
    DB->>DB: роль берётся ИЗ ПРИГЛАШЕНИЯ<br/>фильтрует поля<br/>пишет case.view в журнал
    DB-->>A: только разрешённые поля
    A-->>F: экран роли

    B->>A: «отозвать доступ»
    A->>DB: revoke_invite(id)
    DB->>DB: отзыв + закрытие живых сессий
    Note over F: следующий запрос → «ссылка недействительна»
```

**Почему роль не передаётся аргументом.** Раньше передавалась — и это была дыра: держатель законной семейной ссылки мог запросить то же дело «от имени bestatter» и получить всё. Теперь роль читается из строки приглашения на сервере, а `id дела` наружу не отдаётся вообще.

## 6. История миграций — включая два бага, найденных на боевой базе

```mermaid
flowchart LR
    M1["0001<br/>схема"] --> M2["0002<br/>RLS"] --> M3["0003<br/>доступ по ролям"]
    M3 --> M4["0004<br/>ЗАКРЫТИЕ ДЫР"]
    M4 --> M5["0005<br/>добор прав"]
    M5 --> M6["0006<br/>тупик"]
    M6 --> M7["0007<br/>верное решение"]

    style M3 fill:#c0392b,color:#fff
    style M4 fill:#2b59d1,color:#fff
    style M6 fill:#8a6d3b,color:#fff
    style M7 fill:#3ecf8e,color:#000
```

**0003 была дырявой.** В PostgreSQL `CREATE FUNCTION` по умолчанию раздаёт право вызова роли `PUBLIC`. Функции фильтрации обходили RLS (`SECURITY DEFINER`), и права у них никто не отзывал — аноним мог вызвать их напрямую и получить всё. Проверено на боевой базе перед применением 0004: дыра была настоящей.

**0004 закрыла обе дыры.** Внутренние функции уехали в схему `app`, куда у анонима нет доступа; старые функции **удалены**, а не заменены (замена с новой сигнатурой оставила бы старую версию живой); токены стали храниться хешем; появились сессии и журнал.

**0005 — недобор прав.** Две триггерные функции создаются в 0004 уже после блока прав и остались без ACL. Не эксплуатировалось, но инвариант надо держать: известный шум прячет настоящий сигнал.

**0006 → 0007 — самое интересное.** Обнаружилось, что **дело нельзя было удалить вообще**:

```mermaid
flowchart TB
    D["delete from cases"] --> CASC["каскад удаляет<br/>строки журнала"]
    CASC --> TRIG{"триггер<br/>неизменяемости"}
    TRIG -->|"DELETE запрещён"| FAIL["отказ"]

    D2["попытка 0006:<br/>SET NULL вместо каскада"] --> UPD["но SET NULL — это UPDATE"]
    UPD --> TRIG2{"тот же триггер"}
    TRIG2 -->|"UPDATE тоже запрещён"| FAIL2["снова отказ"]

    FIX["0007: убрать внешний ключ<br/>у журнала совсем"] --> OK["дело удаляется,<br/>журнал остаётся"]

    style FAIL fill:#c0392b,color:#fff
    style FAIL2 fill:#c0392b,color:#fff
    style OK fill:#3ecf8e,color:#000
```

Два правильных по отдельности правила заклинивали друг друга. Для отрасли под DSGVO это блокер — статья 17 требует возможности удалить персональные данные. Решение: журнал аудита не должен иметь внешнего ключа на изменяемые данные, потому что он **обязан переживать** то, на что ссылается. Персональных данных в журнале нет — только роль, группы полей, сессия и время.

Проверено: после удаления дела все таблицы с персональными данными пусты, журнал цел.

## 8. Админка платформы — что предлагаю строить

Граница, которую предлагаю зафиксировать раз и навсегда:

```mermaid
flowchart TB
    subgraph ADMIN["Наша админка видит"]
        A1["сколько бюро подключено"]
        A2["сколько дел, в каких фазах"]
        A3["кто кому выдал доступ<br/>и какой роли"]
        A4["активные сессии сейчас"]
        A5["журнал событий"]
        A6["открытые / закрытые дела"]
    end

    subgraph NEVER["Не видит никогда"]
        N1["имя умершего"]
        N2["адрес, конфессия"]
        N3["медицинские отметки"]
        N4["содержимое документов"]
    end

    ADMIN -->|"метаданные"| OK["безопасно и достаточно<br/>для управления платформой"]
    NEVER -->|"содержимое"| STOP["вернуло бы ту самую дыру,<br/>которую закрыли"]

    style ADMIN fill:#0f2417,color:#fff
    style NEVER fill:#2b0f0f,color:#fff
    style STOP fill:#c0392b,color:#fff
```

Вложенность, как ты иописывал — сверху сводка, вглубь по клику:

```mermaid
flowchart LR
    L0["Платформа<br/>всего бюро · дел · активных сессий"]
    L0 --> L1["Регион<br/>Sachsen: 4 бюро, 37 дел"]
    L1 --> L2["Бюро<br/>Haus Nord: 12 дел, 3 активных"]
    L2 --> L3["Дело<br/>M-2026-4318: фаза, участники,<br/>кому выдан доступ"]
    L3 --> L4["Доступ<br/>роль, выдан, использован,<br/>отозвать"]

    style L0 fill:#131416,color:#fff
    style L4 fill:#2b59d1,color:#fff
```

На каждом уровне — только счётчики и связи. На самом глубоком уровне видно, **что доступ существует и кем используется**, но не то, что за ним лежит.
